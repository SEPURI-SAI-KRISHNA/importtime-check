# importtime-check 0.2.0a2

This second 0.2 alpha adds an explicit, reviewable path from complete import
measurement reports to a **candidate** schema-1 baseline. It does not select
thresholds or promote a candidate into approved CI policy. The public API is
still prerelease.

## What's new

- `propose_baseline` accepts a validated comparable cohort, a caller-chosen
  profile, and exactly one `TargetAllowance` for every target. It uses the
  observed upper median of complete-run medians and preserves cohort
  sampling and safe interpreter identity. It does not import targets, infer
  budgets from noise or old policy, or save a file by itself.
- `baseline propose` strictly loads 2–64 complete v1 reports via repeated
  `--file` flags. It requires runner and installation context labels, a
  profile, per-target `--budget MODULE=US,PERCENT` entries, and a new output
  path. It writes canonical schema-1 JSON only after all inputs validate.
  There is no `--replace`; an existing output path fails closed.
- `explain_baseline_proposal` and CLI `--explain` present deterministic,
  path-free review text with source report digests, observed ranges and
  spreads, chosen policy, and the candidate digest. Optional
  `--compare-baseline` names changed identity, sampling, target, median, and
  allowance fields against a separately supplied old baseline. It never
  imports the old allowances or modifies either policy file.
- A pinned, manually dispatched consuming-project example collects reports
  and uploads only candidate/review artifacts. It has read-only repository
  permission and does not commit or change the required PR gate. The
  [candidate review guide](../guides/candidate-review.md) explains how to
  retain the exact source reports separately and approve policy through a
  distinct reviewed PR.
- CI checks the example's trigger, pins, upload paths, and separation from
  the committed baseline gate. It also exercises candidate creation and
  explanation through a clean installed wheel on package and selected
  Windows/macOS lanes. Archived v1 report fixtures remain unchanged.

After publication, install the exact prerelease:

```console
python -m pip install --pre importtime-check==0.2.0a2
python -m pip install --pre "importtime-check[pytest]==0.2.0a2"
```

Before publication, that PyPI pin cannot resolve. Use a clean wheel built
from this reviewed source for verification, and do not upload it manually.
For example, after saving two or more distinct, complete reports:

```console
importtime-check baseline propose --file run-1.json --file run-2.json --runner-context ubuntu24-py311 --install-context locked-build --profile ci-reviewed --budget email=150,20 --budget json=25,10 --output candidate-baseline.json --explain
```

The example budgets illustrate syntax, not recommended limits. Keep the
original report bytes and runner/dependency evidence. A digest proves only
the bytes it names; reported identity and caller-provided context labels do
not prove equal hardware, load, Python patch level, or dependency versions.
Review each allowance and the candidate's entire policy diff before placing
it at the committed path used by `check` or pytest.

## Upgrade and compatibility

The Python floor remains 3.11, with CPython 3.11–3.14 in the tested matrix.
The core still has no runtime dependencies; pytest remains an explicit
optional extra. Existing `measure`, `baseline record/show/refresh`, `check`,
and pytest behavior and exit codes do not change. Archived v1 measurement
reports from `0.1.0a4` and offline cohort analysis from `0.2.0a1` remain
supported. Approved schema-1 baselines need no migration. A proposed
candidate has that same schema, but its new file path and separate human
review are the approval boundary; raw reports and review text are never
accepted as a baseline by `check`.

To upgrade a consuming project, deliberately update its exact tool pin to
`0.2.0a2` **after publication** while retaining the existing approved
baseline and gate. Use the [measurement guide](../guides/measurement-artifacts.md)
to collect reports, the [candidate review guide](../guides/candidate-review.md)
to evaluate a proposal, and the [CI baseline guide](../guides/ci-baselines.md)
for the committed policy gate. The example workflow does not upload its
temporary source reports, so obtain exact evidence separately before
approving a candidate. No part of this release automatically refreshes,
commits, or widens reviewed thresholds.
