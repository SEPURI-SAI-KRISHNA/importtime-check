# importtime-check 0.1.0a3

This third alpha makes reviewed per-target import-time budgets practical for
multi-module baselines. It adds recording inputs, not a new baseline format or
regression rule. The public API is still prerelease and may change before 1.0.

## What's new

- The public immutable `TargetAllowance` value holds one target's absolute
  microsecond and percentage allowances. `record_baseline` accepts an exact
  `per_target_allowances` mapping as an alternative to its existing common
  pair. Every observed module needs one named allowance; missing, unknown,
  mixed, or invalid inputs fail before a baseline is constructed.
- `importtime-check baseline record` accepts repeated
  `--budget MODULE=US,PERCENT` options. It checks the full module/budget
  association before probing or importing, then prints sorted, normalized
  allowances and asks the user to review the resulting file diff.
- The [CI baseline guide](https://github.com/SEPURI-SAI-KRISHNA/importtime-check/blob/main/docs/guides/ci-baselines.md)
  and pinned consuming-project workflows show two installed modules with
  different illustrative budgets. A manual workflow uploads a candidate;
  the PR gate reads only a separately reviewed, committed baseline.

For a local syntax trial after installing the release, use standard-library
targets; these numbers are examples, **not** recommended CI thresholds:

```console
importtime-check baseline record --output importtime-local.json --module email --module json --budget email=150,20 --budget json=25,10 --profile local-review
importtime-check baseline show --file importtime-local.json
importtime-check check --baseline importtime-local.json --module email --module json --profile local-review
```

`email` stores 150 us and 20%; `json` stores 25 us and 10%. Recorded medians
come from fresh samples, not these allowances. A later `check` may return `1`
when either target exceeds **both** of its own allowances. Use comparable
runners and repeated observations to choose reviewed budgets; a passing run
does not approve them automatically.

## Install and upgrade

After publication, install the exact prerelease. Install the optional pytest
extra only if you use that integration:

```console
python -m pip install --pre importtime-check==0.1.0a3
python -m pip install --pre "importtime-check[pytest]==0.1.0a3"
```

Upgrade an exact earlier-alpha pin deliberately in your lock file. The
baseline JSON format and check report remain schema 1; existing baselines
load without migration. Existing common-allowance Python and CLI calls keep
working. `baseline refresh --replace` remains timing-only and preserves every
target's stored allowance. Changing targets, identity, sampling, or allowances
requires an explicitly reviewed `baseline record --replace` or policy edit;
neither `check` nor pytest learns or rewrites budgets. An existing output file
is never replaced implicitly, and invalid input leaves its bytes unchanged.

The core package still has no runtime dependencies. Pytest integration remains
opt-in and is not loaded automatically. The minimum Python version remains
3.11, with CPython 3.11 through 3.14 in the tested matrix. CLI `check` exit
codes remain `0` for pass, `1` for regression, and `2` for invalid input or
operational failure.

## Limits and review

Measurements use fresh isolated CPython processes and report the target's
import-time diagnostic, not whole-process startup time. Dependency changes,
host load, and runner differences can alter timings even when recorded
identity matches. Do not copy the guide's example allowances into a real CI
gate without measuring ordinary variance and reviewing each policy change.
